# 后端开发规范（草案 v0.1）

> 状态：**草案 v0.1（2026-08-22，待评审）**。评审通过后作为第 5 批及后续后端实现基线；已合并代码允许按批次逐步治理，但新增能力必须立即遵循。
> 适用范围：`backend/` 下 .NET 解决方案。接口以 `docs/api/` 为唯一事实来源，领域概念变更遵循 `docs/concepts/` 与 ADR。
> 文档关系：本草案是第 5 批综合后端规范评审稿，不立即替代既有《后端工程规范》v1.3。评审通过前若两者冲突，以 docs/guides/后端工程规范.md 为当前生效标准；评审通过后必须将两者合并、去重并升级为唯一长期标准，避免两套规范并行。

## 一、基本原则

1. **契约先行**：端点、DTO、错误码、枚举、权限、分页和幂等先在 `docs/api/` 评审锁定，再实现。
2. **单一职责**：Controller 只做 HTTP/权限/参数到应用服务映射；业务规则、事务和查询在服务层；实体与 EF 配置不承载 HTTP 语义。
3. **数据一致性**：一次业务动作的实体写入、编号、幂等记录、库存流水和附件关联必须在一个事务边界内闭合。
4. **稳定错误**：业务分支以字符串错误 code 表达；message 可以本地化，code 和 HTTP 语义不得随语言变化。
5. **可测试**：核心状态机、并发、幂等、库存守恒必须有单元或 PostgreSQL 集成测试。
6. **最小演进**：优先满足当前工作流，不为未来模块提前建复杂抽象。

## 二、解决方案与目录结构

```text
backend/
  AWms.Api/
    Controllers/       # HTTP 适配层
    Middleware/        # 认证、异常、幂等、语言、JSON 等
    Program.cs         # 组合根
  AWms.Domain/
    Entities/          # EF 实体
    Enums/             # 稳定枚举
    Dtos/<Module>/     # 契约 DTO
    Interfaces/        # 跨层服务接口
  AWms.Infrastructure/
    Data/              # DbContext、迁移、模型配置
    Services/          # 领域/应用服务、事务、编号、查询
  AWms.Tests/          # 单元测试
  AWms.IntegrationTests/ # PostgreSQL + WebApplicationFactory 集成测试
```

### 2.1 依赖方向

```text
Api → Infrastructure → Domain
Tests/IntegrationTests → Api/Infrastructure/Domain
```

禁止：

1. `Domain` 引用 EF 以外的 Infrastructure 具体实现或 ASP.NET MVC 类型。
2. Controller 直接操作 `DbContext`。
3. Service 返回 ActionResult、HttpRequest、HttpResponse 或依赖 Controller 上下文。
4. Integration Test 反向修改生产代码分支。
5. 绕过 `Directory.Packages.props` 私加包版本。
6. 在 API 层保存可变全局业务状态。

## 三、模块划分

1. 模块按业务域划分：主数据、入库单、收货、库存、打印、附件、认证权限、导入导出、元数据。
2. 每个模块具备：Controller、DTO 目录、服务、实体/查询、测试；跨模块能力下沉基础设施。
3. 服务之间可以调用公开方法，但不得读取彼此私有 DTO 或直接改对方实体集合；跨域规则通过显式方法表达。
4. Controller 命名与契约资源一致；一个 Controller 聚焦一个资源或紧密耦合的一组端点。
5. 新增模块流程：
   - 契约文档与权限注册表先锁定；
   - DTO、实体、服务、Controller、迁移、测试小步提交；
   - 更新 API 导航和错误码清单；
   - 集成测试覆盖鉴权、成功、失败和并发/幂等（如适用）。
6. 废弃字段或端点必须先在契约标注替代方案与过渡期，不在实现中静默删除。

## 四、DTO 与契约

1. `AWms.Domain/Dtos` 中的契约 DTO 与 `docs/api/` 字段名、可空性、类型、示例一致。
2. JSON 使用 camelCase；枚举和状态按契约返回稳定字符串值，不序列化数字。
3. 时间：传输 ISO 8601 UTC；日期 `yyyy-MM-dd`。
4. decimal：传输字符串，数据库精度遵循契约（当前 18,4）。
5. ID：UUID。
6. 分页统一 `{ items, total, page, pageSize }`；`pageSize=0` 仅按契约允许全量。
7. 查询、排序和 filter DSL 必须使用白名单，服务端追加确定性排序兜底。
8. 创建、幂等写、状态变更 HTTP 状态码遵循契约；不得所有错误都返回 200。
9. DTO 修改必须同步契约文档、OpenAPI/测试和前端类型；不允许实现先行。
10. 不把数据库实体直接作为公共 API 响应；必须映射 DTO，避免外键、内部状态和迁移字段泄漏。
11. 后端返回的业务原因使用稳定 `reasonCode`；确需同时给人阅读的说明字段必须在契约中定义。

## 五、Controller 与服务规则

### 5.1 Controller

1. 保持薄层：验证路由参数、调用服务、返回 envelope；不写业务 if 分支。
2. 写端点必须使用 `[RequirePermission]` 或等价中间件校验 action 权限；查询端点校验 route 权限。
3. 需要幂等的写端点声明 `RequireIdempotency-Key`，幂等键由统一中间件处理。
4. 不在 Controller 捕获普通业务异常再包装；让异常中间件统一输出。
5. 文件上传/下载必须校验大小、MIME、业务归属和权限。
6. 控制器方法命名表达动作，不以 HTTP 细节命名业务概念。

### 5.2 服务

1. 一个公共方法对应一个业务用例；私有方法表达校验、查询和状态推进。
2. 服务方法显式传递 `CancellationToken`。
3. 跨表业务写入必须明确事务边界；事务内失败回滚全部业务数据。
4. 先校验再写入；不能依赖数据库异常作为常规业务分支。
5. 状态机修改必须集中在一个服务/方法，禁止多个模块直接改同一状态字段。
6. 并发实体使用契约规定的版本或乐观锁；冲突返回 `VERSION_CONFLICT`。
7. 编号生成、幂等记录和业务写入遵循同一事务与重试规则。
8. 服务不读取配置 Section 的散落字符串；使用强类型 Options。
9. 日志记录 code、资源 ID、操作者等结构化字段，不记录密码、token、完整附件内容。

## 六、数据与迁移

1. EF迁移必须版本化，禁止启动时自动 `EnsureCreated` 或手工改库。
2. 模型配置集中在 `DbContext`/配置类；唯一约束、索引、默认值必须与契约和数据规则一致。
3. 时间统一 UTC 存储；数据库默认值不得替代业务显式赋值。
4. decimal 精度、字符串长度、枚举存储方式在迁移中固化。
5. 高频查询字段建立索引；时间性列表默认 `createdAt DESC, id DESC`。
6. 唯一业务键与软删除/历史数据策略必须在契约或概念文档中说明。
7. 迁移必须可从上一版升级，不得编写仅支持空库的初始化脚本。
8. 种子数据仅限管理员、权限注册表等系统必需数据；测试数据放测试工程。
9. 破坏性迁移必须单独评审并提供回滚/备份说明。

## 七、错误处理与 i18n

### 7.1 统一响应

```json
// 成功
{ "code": "OK", "message": "ok", "data": {} }

// 业务失败
{ "code": "ORDER_STATUS_INVALID", "message": "入库单状态不允许该操作。", "data": null }
```

1. 所有响应走统一 envelope；204 端点按契约可不返回 body。
2. HTTP 状态、错误 code、内部 hex 编号遵循 `docs/api/枚举与错误码.md`。
3. 前端只依赖 code 做业务分支；后端 message 用于人可读提示。
4. 未处理异常统一返回 `INTERNAL_ERROR`，不泄漏堆栈、SQL、连接串。
5. 验证错误返回 `VALIDATION_ERROR`，字段级信息如契约要求需结构化，不拼进 message 让前端解析。

### 7.2 DomainException

1. 业务失败抛 `DomainException(code, message/key, statusCode)`，不得用字符串返回值模拟错误。
2. 新增错误码必须先进入契约清单并分配区间/hex。
3. 异常中间件负责日志、HTTP 状态、envelope 和本地化输出。
4. 不用异常做正常控制流；可预期的查询不存在可返回 null/NotFound 并由用例决定结果。
5. 外部基础设施异常转成稳定业务错误或 `INTERNAL_ERROR`，不直接透出第三方文案。

### 7.3 后端消息 localizations

1. 错误文案归后端维护，资源文件建议为 `messages.zh.json` / `messages.en.json`。
2. 词条 key 默认等于稳定错误 code；同一 code 需要按上下文区分时使用 `errors:<code>:<case>` 并在契约或代码清单登记。
3. 词条支持参数占位，例如 `{{quantity}}`、`{{code}}`；不拼接 HTML。
4. 请求语言来自 `Accept-Language`；语言中间件解析 quality，白名单为 `zh`、`en`，未知语言回退 `zh`。
5. 语言只影响 `message` 与后端生成的人可读文档文案；不影响 code、HTTP 状态、排序、数字、日期和枚举值。
6. 词典缺失时回退中文；中文也缺失时使用稳定兜底文案并记录 warning，不得返回空 message。
7. `INTERNAL_ERROR` 中英均不得暴露内部技术细节。
8. 每个新增错误码必须同时补中英词条，并由测试覆盖 zh、en、未知语言回退。
9. 日志记录稳定 code 和参数，不记录已经本地化的 message 作为问题定位主键。

### 7.4 枚举与显示

1. API 数据返回稳定枚举值，不返回本地化显示名。
2. 已契约化枚举由前端 `enums.*` 词条翻译。
3. 后端推荐库位等业务原因返回 `reasonCode`；若必须返回 `reason`，契约必须声明语言行为。
4. 不用数据库中文冗余字段作为唯一语义；需要多语言主数据时先设计契约与存储方案。
5. 打印、导出等由后端生成的人可读内容必须按请求语言输出，并纳入测试。

## 八、认证、权限与安全

1. 所有非公开端点必须认证；授权不只依赖前端隐藏。
2. route/menu/action 三类权限按认证契约执行，写端点必须有 action 权限。
3. 用户、角色、权限、菜单来自注册表，禁止 Controller 硬编码菜单清单。
4. 密码哈希使用项目既有 Argon2 封装；不引入明文/可逆密码。
5. JWT 密钥、连接串等只从环境/配置注入，不入库、不入日志、不入前端。
6. 生产配置缺 secret 必须启动失败，不使用默认弱密钥。
7. 附件 URL 使用短期授权或受保护下载，不暴露物理路径。
8. 上传文件校验扩展名、MIME、大小和业务类型。
9. SQL 只通过 EF 参数化；特殊 SQL 也必须参数化，禁止拼接用户输入。
10. 审计字段记录操作者 ID 与时间；业务流水保证可追溯。

## 九、测试规范

### 9.1 分层

| 类型 | 位置 | 覆盖 |
|---|---|---|
| 单元测试 | `AWms.Tests` | 状态机、校验、编号、查询构造、Token、种子 |
| 集成测试 | `AWms.IntegrationTests` | Controller 契约、权限、事务、PostgreSQL 约束 |
| 契约回归 | IntegrationTests | envelope、错误码、HTTP 状态、DTO 序列化 |
| i18n 回归 | Tests/IntegrationTests | zh/en、fallback、参数 |
| 并发/幂等 | IntegrationTests | 重复提交、乐观锁、事务回滚 |

### 9.2 必测场景

1. 未登录 401、无权限 403、资源不存在 404、业务冲突 409、验证失败 400/422。
2. 写操作重复 `Idempotency-Key` 返回首次结果，不重复入账。
3. 事务失败后主表、行表、库存、流水、编号、幂等记录不产生半提交。
4. 收货/质检/上架等状态机非法迁移被拦截。
5. PostgreSQL 唯一约束、外键、默认排序和分页行为符合契约。
6. `Accept-Language: zh`、`en`、未知语言错误消息输出与回退正确。
7. 枚举/日期/decimal 序列化稳定。
8. 生产必需 secret 缺失时启动失败。

### 9.3 测试纪律

1. 缺陷修复先写失败测试，再修复。
2. 集成测试使用真实 PostgreSQL/Testcontainers，不用 InMemory 掩盖数据库行为。
3. 测试数据在测试内构造，不依赖其他测试执行顺序。
4. 断言契约语义，不断言私有实现细节。
5. `dotnet build`、`dotnet test` 全绿后才可推送；CI 红分支不得提交复验。

## 十、日志、观测与运维

1. 结构化日志包含 traceId、用户 ID、模块、code、资源 ID、耗时。
2. Warning 记录可预期业务失败；Error 记录需要人工处理的系统异常。
3. 不记录敏感数据和完整大对象。
4. 启动日志说明迁移、种子、监听地址等关键步骤。
5. 长任务（导入、打印）要有状态、失败原因和可重试入口。
6. 数据库迁移失败不得继续启动对外提供服务。
7. 部署配置变更必须与 docker compose/CI 一起验证。

## 十一、编码与风格

1. .NET 版本、 nullable、 warnings-as-errors 遵循 `Directory.Build.props`。
2. 文件命名与公开类型一致；一个文件可放紧密相关的多个小 DTO，但不得混跨模块。
3. 命名使用美式英文；业务术语与契约英文一致。
4. 公共成员 XML 文档仅在 API 库必需；不要生成无意义注释。
5. 显式 `readonly`、`record`、`required` 等语言特性，但不为炫技降低可读性。
6. 不提交 commented-out 代码、调试输出和临时分支。
7. 魔法字符串改为常量或枚举；契约错误码/权限码集中登记。
8. 不用 `dynamic`；反射仅限框架扩展点并有测试。

## 十二、提交流程

1. 从最新 `main` 创建 `feat/backend-*` 短命分支。
2. 只基于锁定契约实现；发现缺口写需求回流，由协调者先改文档。
3. 小步提交，Conventional Commits + 中文描述。
4. 契约、迁移、种子、测试与实现尽量同一变更链路，禁止拆出无法独立构建的提交。
5. 完工汇报固定包含：完成范围、实现文件、测试结果、契约偏差、遗留问题、耗时。
6. CI 全绿后才请求集成；不直接 push main。

## 十三、扩展方式示例

| 需求 | 推荐扩展点 |
|---|---|
| 新端点 | 契约 → DTO → Service → Controller → 集成测试 |
| 新错误码 | 错误码契约 → 中英词条 → DomainException → 回归测试 |
| 新枚举 | Domain enum → 契约清单 → 前端显示词条 |
| 新权限 | 注册表 → 角色授权矩阵 → Controller 权限测试 |
| 新查询 | 白名单 + FieldMeta + 标准排序兜底 |
| 新业务事务 | 服务用例 + 幂等 + 事务 + 状态机测试 |
| 新外部系统 | Infrastructure adapter + 稳定错误映射 + 集成测试 |
