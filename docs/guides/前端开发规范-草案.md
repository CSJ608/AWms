# 前端开发规范（草案 v0.1）

> 状态：**草案 v0.1（2026-08-22，待评审）**。评审通过后作为第 5 批及后续前端实现基线；已合并代码允许按批次逐步治理，但新增能力必须立即遵循。
> 适用范围：`frontend/` 下 Web 与 PDA React 前端。业务页面结构以 `docs/design/` 为准，接口以 `docs/api/` 为准。

## 一、基本原则

1. **设计先行**：界面规格未评审通过，不写业务页面代码。
2. **契约先行**：`docs/api/` 是接口唯一事实来源；发现缺口先提需求回流并修订契约。
3. **工作流驱动**：页面和交互从角色工作流推导，不从后端端点清单推导。
4. **平台能力复用**：路由、菜单、权限、布局、标签页、表格、筛选、引用选择器、错误处理统一走平台层。
5. **最小实现**：只做当前批次验收需要的能力，不提前抽象未来框架。
6. **可测可验**：新增行为必须有单元/组件/浏览器测试证据；视觉改动必须提供截图。

## 二、技术栈基线

| 能力 | 约定 |
|---|---|
| UI | React + TypeScript + Vite |
| 路由 | React Router |
| 服务端状态 | TanStack Query |
| 表单 | React Hook Form + zod |
| 样式/组件 | Tailwind + shadcn/Radix + Lucide |
| i18n | i18next / react-i18next |
| HTTP Mock | MSW，仅测试与本地 mock 模式使用 |
| 测试 | Vitest + Testing Library + Playwright Browser Mode |
| 包管理 | pnpm，Node 版本以 `frontend/package.json` 与 `.nvmrc` 为准 |

新增依赖必须说明不可用现有能力解决的原因、包维护状态、体积影响和测试方案；不得同时引入功能重复的库。

## 三、目录与职责

```text
frontend/src/
  api/                 # 契约 DTO、类型化 API 函数、统一 HTTP client
  platform/            # 与业务无关的平台能力
    auth/              # 会话、权限、静默刷新
    i18n/              # 语言初始化（词条仍在 src/i18n/locales）
    layout/            # 顶部导航、标签页栏、内容栏
    tabs/              # 全局工作标签状态与控件
    menu/              # 菜单注册、搜索、导航面板
    route/             # 路由注册与守卫
    table/ filter/ picker/ # 通用列表、筛选、引用选择
  modules/
    web/               # PC 端模块页面
    inbound/           # 入库领域共享页面/组件
    pda/               # PDA 作业端
  components/
    ui/                # shadcn 基础组件
  i18n/locales/        # zh / en UI 词条
  mocks/               # MSW handlers、种子数据；生产不得引用
  lib/                 # 纯工具函数
```

### 3.1 分层依赖方向

```text
modules → platform/api/components/ui/lib
platform → api/components/ui/lib
api → lib/i18n（仅请求头语言）
mocks → api
```

禁止：

1. `platform` 反向依赖业务模块；模块注册由应用组合根完成。
2. 业务模块之间横向 import；共享领域组件下沉到所属领域目录或平台通用组件。
3. 生产代码 import `mocks/`、测试工具、`*.test.*`。
4. 页面直接使用 `fetch`、`axios` 或绕过 `api/client.ts`。
5. 组件内部直接读写 `localStorage`；持久化统一走 `lib/storage` 或平台状态。
6. 复制既有通用组件改业务私有版本；先评估扩展点。

## 四、模块划分与扩展

1. 一个业务模块按“路由注册 + 页面 + 模块私有组件 + hooks + API 类型映射 + 测试”组织。
2. 模块入口只暴露路由、菜单注册和少量公开组件；内部实现不导出到其他模块。
3. 新增页面流程：
   - 界面规格进入 `docs/design/screens/`；
   - 路由/菜单/权限契约进入 `docs/api/`；
   - 前端添加路由注册与页面；
   - 通用能力先判断是否应下沉 `platform/`。
4. 新增全局能力必须说明状态边界、权限关系、缓存释放和测试方式。
5. 模块私有状态不得写入全局 store；跨模块通信优先通过路由参数、Query 缓存或显式 Provider，不使用事件总线私传业务语义。
6. 废弃能力必须保留一个批次的迁移说明，再删除旧路径。

## 五、状态管理

### 5.1 状态分类

| 类型 | 归属 | 示例 |
|---|---|---|
| 服务端状态 | TanStack Query | 列表、详情、待办、用户会话数据 |
| 全局应用状态 | App Provider / Workspace Tabs Provider | 语言、认证状态、全局标签页 |
| 页面/UI 状态 | 页面组件 | 展开筛选、业务标签、Dialog |
| 表单状态 | React Hook Form | 新建/编辑表单 |
| 瞬时派生状态 | `useMemo` | 根据筛选计算统计 |
| 持久化状态 | 显式 storage helper | 语言、上次仓库 |

### 5.2 全局标签页

1. 活动标签列表、activeTabKey、最近使用顺序必须由全局应用层管理。
2. 业务模块只能派发打开、聚焦、更新标题/脏状态、关闭等动作，不直接修改 tabs 数组。
3. 切换菜单不得卸载已有活动标签；页面筛选、分页、滚动和表单输入由保活实例持有。
4. 标签 key 必须稳定且按资源去重；语言切换后标题由 `titleKey + params` 重算。
5. 登录退出后清空标签；刷新/深链接本批只恢复当前标签。
6. 不引入新状态库解决本问题；如 Context +Reducer 产生可测量性能问题，先用 selector/拆分 Provider 优化。

### 5.3 TanStack Query

1. Query key 按资源 + 参数分层，例如 `['inbound-orders', searchBody]`。
2. 同一页面避免重复请求同一 key；列表与详情 key 分离。
3. 写操作成功后只失效受影响资源，不做全量粗暴失效。
4. 错误、加载、空态必须由页面定义；不得依赖全局 spinner 覆盖页面状态。
5. 语言切换不主动清空业务缓存；服务端业务文案如果强依赖语言，不得长期缓存 message。

## 六、契约调用

1. `src/api/types.ts` 与契约 DTO 一一对应，不自行增删字段、不放宽可空性。
2. 每个 API 函数返回明确 DTO 类型；不返回 `any`、`unknown` 或 axios response 包装。
3. HTTP 统一由 `api/client.ts` 处理 envelope、Bearer、`Accept-Language`、超时、401 单飞刷新和 `Idempotency-Key`。
4. 数量 decimal 使用字符串传输；日期 `yyyy-MM-dd`，时间 ISO 8601 UTC；展示格式化走平台 format。
5. 查询空值不发送；分页、排序、filter DSL 遵循 API 通用规范。
6. 契约字段改名、增删、错误码变化必须先有 docs/api 修订记录。
7. Mock handler 与真实契约同步；契约测试发现差异时优先修 mock 或提出回流，不让 mock 变成第二契约。
8. 后端返回的文件路径只按契约处理下载，不猜测静态路径。

## 七、错误处理

### 7.1 错误对象

1. 所有请求异常归一为 `ApiError { code, message, status? }`。
2. 页面不得解析 message 中的中文句子做业务分支；分支只使用稳定错误 code。
3. 网络错误、未知错误使用 `errors.networkError` / `errors.unknownError` 兜底。
4. 401 由 HTTP 层静默刷新和重放；刷新失败清理会话并跳登录，页面不重复处理。
5. 403 展示无权限状态；深链接入口隐藏与后端兜底校验同时存在。

### 7.2 呈现方式

| 场景 | 呈现 |
|---|---|
| 列表/详情加载失败 | 页面错误条 + 重试，保留筛选或上下文 |
| 表单提交失败 | inline 字段错误或 toast；不得清空输入 |
| 删除/作废/危险操作 | AlertDialog 确认 |
| 幂等写操作 | 提交中锁定按钮，失败允许重试 |
| 特定 code 需要刷新 | 静默刷新后给出可行动提示 |
| 后端业务错误 | 默认展示后端 message；前端可为已知 code 增加上下文说明 |

错误提示必须说明发生了什么、用户能做什么；不得只显示“失败”。

## 八、i18n 规范

### 8.1 职责边界

1. 前端维护 UI 文案：导航、按钮、字段、空态、加载、前端校验、枚举显示、错误兜底。
2. 后端维护业务错误消息：错误 code 对应中/英 message，按 `Accept-Language` 返回。
3. 两端不共享词条文件，不通过后端下发整份前端 UI 词条。
4. API 数据返回稳定枚举值/reasonCode，前端负责已契约枚举和 reason 的显示翻译。

### 8.2 词条命名

```text
common.*             # 跨模块动作与状态
nav.*                # 菜单、模块、分组
field.*              # FieldMeta 通用字段
enums.<enum>.<value> # 枚举显示
<module>.*           # inbound/materials/warehouses/...
errors.*             # 仅前端网络/未知错误兜底
```

1. key 用小驼峰；按模块收敛，不新增 `a/b/temp`、编号式或无语义 key。
2. 一个 key 只表达一个文案；组合句子使用 i18next 插值，不用字符串拼接。
3. 动态单号等业务值通过参数传入：`t('inbound.orderTitle', { no })`。
4. 不把中文作为 key；不把英文文案复制为 key。
5. `labelKey` 由契约/FieldMeta 提供，前端必须保证存在。
6. 同一词在多个模块有不同含义时允许模块私有 key；高频完全相同文案才进 `common`。

### 8.3 语言与 fallback

1. 支持语言白名单：`zh`、`en`；默认 `zh`，fallback `zh`。
2. 语言保存于本地存储；登录前后均可切换。
3. 切换立即调用 i18n 更新，不刷新页面，不重置路由和标签状态。
4. 后续请求自动携带 `Accept-Language`。
5. 缺失 key 开发环境输出警告；需提供结构一致性测试，禁止发布裸 key。
6. 语言菜单自身文案用语言原名（中文 / English），不参与当前语言回退。
7. 时间、数量、单位显示遵循契约和视觉规范；不因语言改变业务数值。

### 8.4 缺失治理

1. 新增用户可见字符串必须在同一 PR 添加中英词条。
2. 入库管理、PDA、平台布局在 M5.2 补齐历史缺失。
3. 禁止 `defaultValue` 掩盖生产缺失；仅测试或兼容后端动态 key 时可显式例外。
4. 中英文件结构由测试递归对比；新增语言必须同步扩展类型和语言菜单。

## 九、组件与样式

1. 基础 UI 组件放 `components/ui`，业务组件放模块目录；平台通用组件放 `platform/*`。
2. 组件 props 使用 TypeScript interface/type，回调以 `onXxx` 命名，布尔值避免多含义。
3. 组件文件只导出组件；常量、工具、schema、非组件 hooks 拆独立文件，避免 Fast Refresh warnings。
4. 禁止复制三份以上相似 UI；超过即提取平台组件。
5. 样式使用设计 token 与 Tailwind class；业务样式不得硬编码新色值，语义色走既有映射。
6. 表格中数量、编号、日期使用等宽数字；长单号 ellipsis + tooltip。
7. 触控目标：Web 主操作命中区不小于 32px；PDA 不小于 48px。
8. Dialog、Popover、菜单必须处理焦点圈、Esc、外点击和可访问名称。
9. 不使用装饰性渐变、页面级大阴影和不可关闭的全局 loading。

## 十、路由、权限与菜单

1. 路由注册表声明 path、moduleCode、titleKey、element、标签策略。
2. 登录守卫、权限守卫、403/404 页面统一由平台层提供。
3. 菜单显隐使用登录返回 `menus.web`，并叠加 `route.<moduleCode>` 权限。
4. 后端仍必须校验 action 权限；前端隐藏只是体验优化。
5. 深链接必须可恢复当前工作面，并同步活动标签。
6. 路由参数和 query 不得承载大对象或敏感信息。
7. 模块路由命名遵循小写路径；业务资源详情使用稳定 ID。

## 十一、测试规范

### 11.1 测试分层

| 层 | 覆盖 |
|---|---|
| 单元 | 纯函数、hooks、状态 reducer、格式化、契约映射 |
| 组件 | 表单校验、空/错/加载、权限、可访问性关键行为 |
| 浏览器 | 全局布局、标签保活、路由同步、真实交互 |
| Mock/契约 | MSW handler 与 docs/api DTO 一致 |
| E2E/联调 | 每批核心工作流 Given-When-Then |

### 11.2 必测场景

1. 全局标签打开、去重、聚焦、切换、关闭、dirty 确认、MRU 聚焦。
2. 切换菜单后已有筛选/分页/表单输入不丢失。
3. 菜单搜索权限过滤、键盘选择、打开或聚焦已有标签。
4. 中英切换后菜单、标签、字段、空态、枚举更新；业务状态不丢。
5. 401 刷新、403、网络错误、后端业务错误、提交失败保留输入。
6. 1024x768 和 1440x900 布局不重叠。

### 11.3 测试纪律

1. 测试行为与用户可见结果，不断言内部实现细节。
2. 测试中的 mock 必须契约化；不为让测试通过改返回结构。
3. 每个缺陷修复先写失败用例，再修复。
4. `pnpm lint`、`pnpm build`、`pnpm test` 全绿后才可推送。
5. CI 红分支不得提交复验；推送方负责修复。

## 十二、性能与质量

1. 路由级代码分割按模块执行，平台壳保持轻量。
2. 大列表使用分页/虚拟列表；不得一次性渲染上万行。
3. 图片和 PDF 预览按需加载，保护资源错误要保留占位。
4. 组件导出边界保持 Fast Refresh 有效；dev 启动不得出现 warnings。
5. 不使用 `any`、非必要 `as`、禁用 TS 检查；类型推断不足以表达契约时写显式类型。
6. 不提交调试日志、注释掉的大块代码和临时页面。
7. 用户输入必须前端防呆，同时不能替代后端校验。

## 十三、提交流程

1. 从最新 `main` 创建 `feat/frontend-*` 短命分支。
2. 实现依据为锁定契约、定稿界面规格和当前迭代计划；发现缺口先回流。
3. 小步提交，Conventional Commits + 中文描述。
4. 完工汇报固定包含：完成范围、实现文件、测试结果、契约偏差、遗留问题、耗时。
5. PR 描述附关键截图/录屏和测试证据。
6. 评审通过前不合并；不直接 push main。

## 十四、扩展方式示例

| 需求 | 推荐扩展点 |
|---|---|
| 新列表页 | `platform/table` + FieldMeta + 通用列表模板 |
| 新筛选控件 | FieldType 扩展 + `platform/filter`，不改各页面 |
| 新模块 | 模块目录 + 路由/菜单注册 + 权限契约 |
| 新全局入口 | 顶部导航配置 + 权限 + i18n + 可访问性 |
| 新错误处理分支 | ApiError code 映射，不解析 message |
| 新枚举 | API 契约 + `enums.*` 词条 + 类型联合 |
| 新业务标签 | Workspace Tabs 动作与 key 策略 |
