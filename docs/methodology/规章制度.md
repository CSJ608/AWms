# AWms 规章制度（v0.1，讨论中）

> 本文档是全项目最重要的约定，所有 AI 工具与人共同遵守。
> 状态：讨论中，随项目演进更新。

---

## 一、核心原则（铁律）

1. **愿景先行，产品层驱动工程层**：先想清楚为谁、为什么、做什么流程，再谈界面、契约、实现。页面由"角色的工作流"派生，不由 API/模块清单派生。
2. **每阶段只回答一个问题**：愿景 → 角色与工作流 → 界面规格 → 契约 → 并行实现与验收。每阶段产出小而完整，门禁通过才进入下一阶段。
3. **标准文档固定位置，迭代/过程文档归档隔离**：标准文档永不归档、永远可查；迭代文档验收后归档；过程状态不入 git。
4. **规格进文档，状态进工具**："做到哪了"看 git 和交接快照，不写进长期文档。
5. **"已完成"以 git 和测试为准**，不以文档为准；文档里的状态会过期。
6. **契约先行**：前后端唯一依据是 docs/api/ 契约；契约锁定后双方才并行开工。
7. **先设计后实现**：界面规格（含视觉）定稿并评审通过，前端才允许写代码。
8. **每批 = 一条可演示的工作流**：批内先设计后实现，批末"功能验收 + 视觉验收 + 演示"，不攒批。

## 二、五阶段模型

| 阶段 | 只回答的一个问题 | 产出物（标准目录） | 门禁 |
|---|---|---|---|
| 1 愿景 | 为谁解决什么问题，成功长什么样 | docs/product/vision.md | 用户确认 |
| 2 角色与工作流 | 谁在什么场景按什么顺序做事 | docs/product/roles/、docs/product/workflows/ | 用户确认流程无缺步 |
| 3 界面规格 | 每屏长什么样、有哪些状态、怎么交互 | docs/design/screens/、docs/design/视觉规范.md | **视觉评审通过，前端才开工** |
| 4 契约 | 前后端怎么对接 | docs/api/*.md + 概念设计 | 双方确认可并行 |
| 5 实现与验收 | 能否在真实环境跑通这条工作流 | 代码 + 测试 + 演示 | 每批验收记录 + 回顾 |

- 阶段 1-3 是"设计层"，产出长期标准；阶段 4 是"对接层"；阶段 5 是"实现层"。
- 设计层可以边讨论边修订，但进入阶段 5 前必须定稿并评审。

## 三、迭代节奏

- **设计批与功能批交替**：项目启动先做设计批（愿景 + 角色 + 工作流 + 首页/收货示例界面规格）；之后每个功能批只做 1-2 条工作流。
- 迭代按"需求批次"划分，不固定时间。一批 = 计划 + 详设/界面规格 + 实现 + 验收 + 回顾。
- 批次验收后：迭代文档整套归档到 iterations/archive/，active/ 只保留当前一批。

## 四、评审与门禁

| 门禁 | 对象 | 通过标准 |
|---|---|---|
| 愿景评审 | vision.md | 用户确认方向 |
| 流程评审 | 工作流文档 | 用户确认步骤、异常路径完整 |
| 视觉评审 | 界面规格/高保真原型 | 用户确认视觉达标 |
| 契约评审 | api/ 契约 | 前后端都确认可据此开工 |
| 批验收 | 本批工作流 | 功能 Given-When-Then + 视觉对照 + 演示 |

- 评审记录写入 docs/reviews/（按日期归档，快照性质）。
- 前端视觉评审必须有**截图/原型**作为依据，不能只凭文字描述。

## 五、AI 协作约定

- **分工**：
  - 产品/设计 Agent：愿景、角色、工作流、界面规格、视觉评审
  - 后端 Agent：契约细化、领域实现、测试
  - 前端 Agent：mock 数据层、页面实现、联调
  - 人（用户）：各门禁的评审者与最终决策者
- **会话开始**：先读 AGENTS.md → _handoff.md → 当前批次计划 → 按需读标准文档。
- **提交约定**：Conventional Commits + 中文描述；批次提交 `feat: 实现第X批 - <概要>`。
- **需求回流**：实现中发现契约/规格缺口 → 写成回流单（场景/缺口/建议）→ 评估 → 决策 → **先改标准文档（api/ 或 design/）** → 再改代码。不得绕过规格自造字段或私加交互。

## 六、测试与部署

- 测试金字塔：少量 E2E / 中等集成 / 大量单元；核心业务逻辑严格 TDD。
- 环境：dev（本地）/ test（模拟生产）/ prod（正式，保留人工确认）。
- 数据库迁移版本化；容器化 + CI/CD（建设时机按批次计划推进）。
