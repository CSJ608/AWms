# AWms 规章制度（v0.4，已定稿）

> 本文档是全项目最重要的约定，所有 AI 工具与人共同遵守。
> 状态：已定稿 v0.4（2026-08-11）。

---

## 一、核心原则（铁律）

1. **愿景先行，产品层驱动工程层**：先想清楚为谁、为什么、做什么流程，再谈界面、契约、实现。页面由"角色的工作流"派生，不由 API/模块清单派生。
2. **每阶段只回答一个问题**：愿景 → 角色与工作流 → 界面规格 → 契约 → 并行实现与验收。每阶段产出小而完整，门禁通过才进入下一阶段。
3. **标准文档固定位置，迭代/过程文档归档隔离**：标准文档永不归档、永远可查；迭代文档验收后归档；过程状态不入 git。
4. **规格进文档，状态进工具**："做到哪了"看 git 和交接快照，不写进长期文档。
5. **"已完成"以 git 和测试为准**，不以文档为准；文档里的状态会过期。
6. **契约先行**：前后端唯一依据是 docs/api/ 契约；契约锁定后双方才并行开工。
7. **先设计后实现**：界面规格（含视觉）定稿并评审通过，前端才允许写代码。
8. **每批 = 一条可演示的工作流**：批内先设计后实现，批末"功能验收 + 视觉验收 + 演示"，不攒批。

## 二、五阶段模型

| 阶段 | 只回答的一个问题 | 产出物（标准目录） | 门禁 |
|---|---|---|---|
| 1 愿景 | 为谁解决什么问题，成功长什么样 | docs/product/vision.md | 用户确认 |
| 2 角色与工作流 | 谁在什么场景按什么顺序做事 | docs/product/roles/、docs/product/workflows/ | 用户确认流程无缺步 |
| 3 界面规格 | 每屏长什么样、有哪些状态、怎么交互 | docs/design/screens/、docs/design/视觉规范.md | **视觉评审通过，前端才开工** |
| 4 契约 | 前后端怎么对接 | docs/api/*.md + 概念设计 + ADR | 双向评审无异议、契约锁定 |
| 5 实现与验收 | 能否在真实环境跑通这条工作流 | 代码 + 测试 + 演示 | 每批验收记录 + 回顾 |

## 三、迭代节奏

- **设计批与功能批交替**；每个功能批只做 1-2 条工作流。
- 迭代按"需求批次"划分，不固定时间。一批 = 计划 + 设计/契约 + 实现 + 联调 + 验收 + 回顾。
- 批次验收后：迭代文档整套归档到 iterations/archive/，active/ 只保留当前一批。

## 四、评审与门禁

| 门禁 | 对象 | 通过标准 |
|---|---|---|
| 愿景评审 | vision.md | 用户确认方向 |
| 流程评审 | 工作流文档 | 用户确认步骤、异常路径完整 |
| 视觉评审 | 界面规格/原型 | 用户确认视觉达标 |
| 契约评审 | api/ 契约 | **双向评审无异议**（见 §八） |
| 批验收 | 本批工作流 | 功能 Given-When-Then + 视觉对照 + 演示 |

- 评审记录写入 docs/reviews/（按日期归档，快照性质）。
- 前端视觉评审必须有**截图/原型**作为依据，不能只凭文字描述。

## 五、AI 协作约定

- **分工**：
  - 产品/设计 Agent：愿景、角色、工作流、界面规格、视觉评审
  - 后端 Agent：契约细化、领域实现、测试、测试环境
  - 前端 Agent：mock 数据层、页面实现、联调执行
  - 协调者（AI）：文档流转、意见汇总、问题归属、交接快照
  - 人（用户）：各门禁的评审者与最终决策者
- **会话开始**：先读 AGENTS.md → _handoff.md → 当前批次计划 → 按需读标准文档。
- **提交约定**：Conventional Commits + 中文描述；批次提交 `feat: 实现第X批 - <概要>`。
- **需求回流**：实现中发现契约/规格缺口 → 回流单（场景/缺口/建议）→ 评估 → 决策 → **先改标准文档（api/ 或 design/）** → 再改代码。不得绕过规格自造字段或私加交互。

## 六、测试与部署

- 测试金字塔：少量 E2E / 中等集成 / 大量单元；核心业务逻辑严格 TDD。
- 环境：dev（本地）/ test（模拟生产）/ prod（正式，保留人工确认）。
- 数据库迁移版本化；容器化 + CI/CD（建设时机按批次计划推进）。

## 七、文档分类与归档

- 长期标准：product/、design/、concepts/、decisions/、api/、guides/、methodology/ —— 固定位置，永不归档。
- 迭代文档：iterations/active/ → 验收后移入 iterations/archive/<第X批-名称>/，头部加已归档说明，正文不再修改。
- 过程/状态：reviews/（按日期归档）、methodology/_handoff.md（不入 git）。

## 八、前后端协作与联调机制（定稿 2026-08-10，用户确认）

### 8.1 角色与职责

| 角色 | 职责 |
|---|---|
| 人（你） | 方向、门禁裁决、最终验收；不写代码细节 |
| 协调者（AI） | 维护文档流转、收集评审意见、裁决问题归属、管交接快照 |
| 后端 AI | 契约实现、领域逻辑、测试、测试环境可用 |
| 前端 AI | mock 数据层、页面实现、**联调执行（默认集成负责人）** |

### 8.2 开工门禁（每批开工前）

1. 本批设计/契约产物就绪（概念 / 契约 / 界面规格 / 标签规范）。
2. **双向评审**：前端 AI 与后端 AI 各自通读全部相关文档，输出《开工评审意见》（冲突点 / 缺口 / 建议 / 无异议）。
3. 协调者汇总 → 人逐条决议（采纳 / 拒绝 / 延后）→ **先更新标准文档**。
4. 门禁：**双方无异议 + 契约锁定** → 前后端一起开工。
5. 评审记录入 docs/reviews/。

### 8.3 双轨并行

- 前端基于 **mock 数据层**（与契约严格一致）开发，不依赖后端环境。
- 后端按契约实现 + 测试；两端独立提交、独立测试绿。
- 契约是唯一依据；发现缺口走"需求回流"，不得自造字段/端点。

### 8.4 联调（默认前端 AI 负责）

- 每批指定**集成负责人**（默认前端 AI），在批次计划中写明。
- 联调内容：环境就绪（后端 AI 启动测试环境 + 迁移 + 冒烟，集成负责人验证）；种子数据（集成负责人经真实 API 造，幂等可重跑）；全链路跑通（本批工作流 Given-When-Then 用例）；数据核对 + 控制台零报错。
- 产出：联调记录 + 问题清单（入批次计划"反馈与决议"）。

### 8.5 问题归口

| 问题类型 | 谁改 | 流程 |
|---|---|---|
| 契约问题（字段/语义/错误码） | **先改契约文档**（提出方起草、协调者确认），实现方按新契约改 | 需求回流单 |
| 后端 bug（实现与契约不符） | 后端 AI + 回归测试 | 问题清单 |
| 前端 bug（与界面规格不符） | 前端 AI | 问题清单 |
| 环境/部署问题 | 后端 AI 修复，集成负责人验证 | 问题清单 |
| 优先级 | P0（数据错误/流程阻塞）当日处理；P1 本批内；P2/P3 记后续批 | — |

### 8.6 验收与归档

1. 集成负责人提交联调报告；
2. **人验收**：功能（Given-When-Then）+ 视觉（对照界面规格截图/录屏）；
3. 填验收记录 → 批次归档；未通过 → 问题清单回流，修复后复验。

### 8.7 沟通载体（AI 之间不直接改对方代码）

| 载体 | 用途 |
|---|---|
| docs/api/ 契约 | 唯一依据 |
| docs/iterations/active/ 批次计划 | 当前目标 + 问题清单/反馈决议 |
| docs/methodology/_handoff.md | 状态快照（不入 git） |
| docs/reviews/ | 评审/联调记录 |

### 8.8 异地工作区协作规范（2026-08-10 定）

适用：前端/后端 AI 分别在独立工作区 clone 项目、按文档开工、完工提交的配合方式（第 3 批起启用）。

1. **工作区约定**：前端 C:\build\f、后端 C:\build\b；每批开始时从 main 拉最新（clone 或 pull）。
2. **分支策略**：各自开短命分支（feat/frontend-<批次>、feat/backend-<批次>）；**不直接 push main**；完工 push 分支并提交完工汇报。
3. **实现依据**：锁定契约（docs/api/）+ 界面规格 + 迭代计划；**docs/ 只读**——发现问题写问题清单，由协调者裁决后统一改文档（防双方改文档冲突）。
4. **完工汇报模板（固定 6 项）**：① 完成范围（对照迭代计划需求清单）；② 实现文件清单；③ 测试结果（后端 dotnet test / 前端 pnpm build+lint+test）；④ 契约偏差与需求回流（无则写无）；⑤ 遗留问题；⑥ 耗时。汇报写入 docs/reviews/ 或 PR 描述。
5. **测试绿才提交**；不互相改对方代码。
6. **集成回顾（批末）**：双方完工后，用户开新会话由协调者对照锁定契约/界面规格逐项核对前后端 → 输出问题清单 → 人裁决 → 修复 → **合并 main** → 批验收记录 → 归档。
7. 状态进交接快照（_handoff.md）。

### 8.9 分支与 CI/CD 规范（2026-08-11 定）

**分支类型与可写权限**：

| 分支 | 可写 | 用途 |
|---|---|---|
| main | 仅审核者 | 定稿文档（方案/契约/计划/评审意见）+ 集成结果；**禁直接 push**（GitHub 分支保护：要求 PR + backend/frontend 状态检查） |
| review/<批次> | 前端 + 后端 + 审核者（三方） | 意见交换（纯 docs）：方案评审意见、完工评审回应、问题清单；批次验收后合并回 main 随批次归档 |
| feat/frontend-* / feat/backend-* | 各侧 | 开发、任务化提交、返工修复；CI 在 push 时自动跑 |
| integration/<批次> | 仅审核者 | 集成前后端 feat、跑集成 CI + 联调冒烟；验收后合并 main |
| docs/*（可选） | 仅审核者 | 零星文档修订 |

**CI**：push 到 feat/**、main 及任何 PR 触发——后端 dotnet build + test（集成测试 Testcontainers PostgreSQL）；前端 pnpm lint + build + test。**红分支纪律**：分支推送后由推送方等 CI 全绿才算完成；远端 CI 失败视为本地自测不充分，推送方自查修复；红分支不得提交复验。

**CD**：仅 main push（即 PR 合并后）且前后端门禁全绿 → self-hosted runner（标签 awms-test）执行 docker compose 部署测试环境（db 5434 / api 5081 / web 8082），api 启动即自动应用迁移与初始管理员。

**合并**：feat → integration → main 均由审核者通过 GitHub PR 执行；main 启用分支保护（要求 PR + 状态检查 + 禁直接 push）。

**归档联动**：批次验收后按 docs/README.md 归档机制执行（active/、reviews/、review/<批次> 意见文档移入 archive/<第X批-名称>/）。

**测试环境与生产**：test 环境 CI 绿即自动部署；prod 保留人工确认，不做全自动部署。
