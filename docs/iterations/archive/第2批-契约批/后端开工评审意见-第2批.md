# 后端开工评审意见

## A. 技术选型

### A-1：.NET 10 LTS + EF Core + PostgreSQL

**无异议**。ADR-004 已由用户确认，ASP.NET Core Web API + EF Core + PostgreSQL 的选型对内部原型规模（SKU ≤10 万、日单据 ≤2000、≤50 用户）完全胜任。EF Core 迁移策略方面，评审输入强调"版本化、决不让 AI 在非空表乱改结构"——这是正确方向，但契约文档均未涉及迁移版本化细节，属于实现层约定（见下方建议）。

**建议**：开工前补充 `.claude/rules/` 或项目级约束：① EF Core 迁移文件须人工 review 后再执行；② 禁止 AI 对已有表执行 `DROP COLUMN` / `ALTER COLUMN` 型迁移（仅允许 `ADD COLUMN` nullable + 新表）；③ 迁移文件用时间戳命名（EF Core 默认行为，确认即可）。

---

### A-2：附件本地存储路径/权限

**缺口**：附件契约（附件.md）规定"本地文件系统 + 元数据表"且"文件路径不入契约"，但未定义存储根路径的配置方式、目录结构规则（按日期分桶？按 bizType？）、文件清理策略（已关联删除保护后物理文件是否同步删？）。这些不定义会导致：① 不同环境路径不一致；② 百万级附件后单目录性能崩。

**建议**：开工前明确定义（可入 ADR-004 修订或单独实现约定）：① 存储根路径通过 `appsettings.json` 的 `Storage:AttachmentsRoot` 配置；② 子目录按 `bizType/yyyy/MM/` 分桶（避免单目录文件数爆炸）；③ 文件名为 `{uuid}.{ext}`（不用原始文件名，防路径穿越）；④ 物理删除与元数据删除解耦——元数据删后文件可异步/定时清理。

---

### A-3：PDF 生成方案

**缺口**：打印契约声明"后端生成 PDF"，但未指定 PDF 库。.NET 生态可选方案差异大：QuestPDF（MIT、C# fluent API）、PuppeteerSharp（Chromium headless、HTML→PDF）、iTextSharp（商业许可限制）。

**建议**：推荐 **QuestPDF**（纯 C#、无需外部进程、MIT 许可、适合固定模板+二维码场景）。若需 HTML 模板渲染则补 PuppeteerSharp（但引入 Chromium 依赖，对部署环境有要求）。二选一写入实现约定即可。

---

### A-4：密码哈希算法

**建议**：ADR-005 写 "Argon2id/bcrypt"，建议收敛为 **Argon2id**。理由：① Argon2id 是 2015 年 PHC 冠军、抗 GPU/ASIC、抗 side-channel；② .NET 可通过 `libsodium-core`（NaCl）或 `Konscious.Security.Cryptography.Argon2` 使用；③ bcrypt 虽成熟但对长密码截断 72 字节且 GPU 抗性弱于 Argon2id。若不引入第三方库，ASP.NET Core Identity 的 `PasswordHasher`（PBKDF2-SHA256/512）也是可接受的备选。

---

### B-2：Sequence 表 + 原子自增并发正确性

**无异议**。通用规范 2.9 明确 `UPDATE...RETURNING`（行锁）+ `(type,scopeKey,bizDate)` 唯一约束——这是 PostgreSQL 下最可靠的原子自增方案，性能与正确性兼备。

**建议**：实现时注意 `bizDate` 的跨天切换逻辑——当 `resetPeriod=DAILY` 时，当日首次取号应 INSERT 新行（lastNo=1），而非 UPDATE 旧行。建议封装为 `NumberingService.Next(type, scopeKey, count)` 返回 `string[]`，内部：

```sql
INSERT INTO Sequence (...) VALUES (..., @count)
ON CONFLICT (type, scopeKey, bizDate) DO UPDATE
SET lastNo = Sequence.lastNo + @count
RETURNING lastNo
```

单条 SQL 覆盖"首日插入"与"同日自增"两种路径。

---

### B-3：批次系统自动生成

**无异议**。批次契约 v0.3 与概念设计 v1.0 一致：收货时创建（NEW）、生产退料复用（扫描 t=B → 查已有 batchNo）。

**建议**：生产退料复用原批次时，若原批次状态为 AVAILABLE（非待检），退货入库应走"待检"状态——即创建新 StockSubject（同 material + batchNo + PENDING_INSPECTION），而非修改原可用主体。概念设计 §七 已写明此规则，实现时注意不要直接修改原 subject 的状态。

---

### B-4：编号规则注册表实现方式

**建议**：通用规范 2.9 的注册表是**配置数据**而非**硬编码常量**。实现建议：① 用 `NumberRule` 实体表存储（type 为主键），`appsettings` 或种子数据初始化 6 条规则；② `NumberingService` 按 type 查规则后编排 format；③ `formatter` 用策略模式（`IFormatter` 接口，默认 `PrefixDateSeqFormatter`，未来 HU 复合规则新增实现）。这样做到了"规则可插拔"的设计原则，避免硬编码 switch(type)。

---

### B-5：ReceiptLine.orderLineId 的歧义消除

**无异议**。数据模型 v0.4 新增 `orderLineId` + 收货契约 v0.2 明确"优先 orderLineId 匹配"，彻底消除了"同物料多行 → 无法确定是收哪行"的问题。标签规范 v0.11 的 `ol` 字段直接提供 orderLineId，闭环完整。

---

### B-6：Batch 状态枚举缺失

**缺口**：数据模型草案中 Batch 有 `status` 字段，批次契约 DTO 示例显示 `"status": "ACTIVE"`，但**枚举与错误码 v1.5 未定义 Batch 状态枚举**。库存主体状态有 PENDING_INSPECTION/AVAILABLE/FROZEN，但这是 StockSubject 的状态，不是 Batch 的状态。

**建议**：明确 Batch.status 的枚举值（建议 ACTIVE/INACTIVE）并补入枚举文档。若本期批次只有 ACTIVE 一种状态（系统创建后不可删除/停用），也应在枚举文档中注明"本期仅 ACTIVE，后续预留"。

---

### B-7：收货单 (Receipt) 状态流转逻辑未文档化

**缺口**：枚举定义了收货单状态 RECEIVING/CHECKING/PUTAWAY/DONE，但收货契约没有文档化状态流转的条件：

- RECEIVING → CHECKING：何时触发？是首次质检提交？还是自动按行状态聚合？
- CHECKING → PUTAWAY：何时触发？是全部行 CHECKED？
- PUTAWAY → DONE：是否全部行 PUTAWAY_DONE 时自动推进？

**建议**：在收货契约中补收货单状态机定义（类似入库单.md 中的状态机图），明确"聚合推进"规则——如"所有行状态均为 X 时，收货单自动 → Y"。

---

## C. 并发一致性/边界

### C-1：同一事务内"更新物理库存 + 追加流水"

**无异议**。收货契约 §一-8 明确"同一事务——创建内部批次 → 库存主体（待检）→ 物理库存（staging）→ 流水（外部操作）"。质检契约和上架契约同理。EF Core 的 `SaveChangesAsync` + `DbContextTransaction` 完全支持此模式。

**注意**：质检和上架是**独立请求**（独立事务），不是与收货合并。评审输入中"收货/质检/上架同一事务内"容易误读为三个操作合并——正确理解是**每个操作内部**的物理库存更新与流水追加同事务。契约端点设计确认这是独立操作（POST /api/receipt-lines/{lineId}/quality-check、POST /api/putaway-records），无冲突。

---

### C-2：复式记账——内部操作组内求和=0

**建议**。概念设计 v1.0 §五 定义了"内部操作组内求和=0"规则（移库：staging -1 + target +1 = 0；状态变更：待检 -1 + 可用 +1 = 0）。实现层面：

- **强制点**：建议在应用层同事务内校验——插入组内全部 Ledger 行前，检查 `SUM(quantity) = 0`（内部操作）或允许非零（外部操作）。不需要 DB CHECK 约束（跨行聚合约束在 SQL 层面实现复杂且错误信息差）。
- **TxnGroup.type** 字段已在数据模型中出现但枚举未定义——建议补充：`EXTERNAL_IN`（入库）、`EXTERNAL_OUT`（出库）、`INTERNAL_TRANSFER`（移库）、`STATUS_CHANGE`（状态变更）。

---

### C-3：物理库存 version 乐观锁

**无异议**。PhysicalInventory.version + VERSION_CONFLICT 错误码（0x030105）设计正确。前端约定也明确了 CONFLICT → "静默刷新"的处理策略（枚举与错误码 §三）。

**建议**：EF Core 实现用 `[Timestamp]` 或 `IsRowVersion()` 属性，`DbContext` 自动将 version 纳入 UPDATE WHERE 子句，`DbUpdateConcurrencyException` 映射为 VERSION_CONFLICT 响应。不要在应用层手动检查 version 字段。

---

### C-4：Idempotency-Key 实现

**缺口**：通用规范 2.6 定义了"写操作 Idempotency-Key"的语义（重复返回首次结果），但未定义存储与过期机制。

**建议**：

- **存储**：建 `IdempotencyRecord` 表（`key` PK, `responseCode`, `responseBody` JSONB, `expiresAt`），写操作开始时在**同一事务**内 `INSERT` 幂等键（利用 PK 防竞态），其他并发请求遇 PK 冲突 → 等事务提交后返回已存响应。
- **过期**：`expiresAt = createdAt + 24h`，定时清理过期记录。
- **范围**：适用于 POST /api/receipts、POST /api/receipt-lines/{id}/quality-check、POST /api/putaway-records 等写操作。GET/查询类不需要。

---

### C-5：唯一码生成+登记+打印同事务

**无异议**。打印契约 §四-3 已明确"与业务同事务登记（避免孤儿码）"。POST /api/print/unique-labels 的行为——编号服务 NextN → INSERT UniqueCode (UNRECEIVED) → 返回 PrintJob——在同一事务内，若事务回滚则序号跳号（已允许的代价），但不会产生孤儿码。

**建议**：唯一码打印还隐含一个并发点——若两个操作员同时为同一行打印唯一码，可能产生不连续的码集。建议将 `inboundOrderLineId` 纳入幂等键或加行级锁，避免并发冲突。

---

### C-6：严格/宽松策略的校验点

**无异议**。入库单契约 §二 明确：

- PO=STRICT：`quantity == expectedQty`（行级校验，整行一次收齐，不可拆分）；行与行独立（不同行可分次收货）。
- PR/OT=LENIENT：按实收记录 diff，允许超收。

**建议**：STRICT 场景的 QTY_MISMATCH_STRICT 错误码（0x020203）定义清晰。实现注意：**严格策略下同单不同行可以分次收**（不要求一张收货单收完全部行），仅**单行不可拆分**。这个语义目前只在入库单 ¶二 的 prose 中描述，建议在收货契约的 POST /api/receipts 中补一句行为说明。

---

### C-7：入库单 RECEIVED 终态推进

**缺口**：入库单状态 RECEIVED 的定义是"所有行被收货单覆盖后自动推进"，但这个"自动推进"的触发机制未明确：

- **方案 A**（推荐）：收货提交事务内，检查所有行 `SUM(ReceiptLine.actualQty) >= expectedQty`（严格）或 `SUM(actualQty) >= expectedQty`（宽松任意覆盖），满足 → 推进为 RECEIVED。
- **方案 B**：异步/定时任务推进（不推荐——用户看到状态延迟）。

**建议**：采用方案 A（同事务推进），在收货契约中明确。

---

### C-8：导入两阶段——预校验与执行间的时间窗竞态

**建议**：导入导出契约规定"预校验不落库 → 全部通过才执行"。但预校验到执行之间存在时间窗——在此期间另一个用户可能创建了同 code 的物料，导致预校验通过但执行时唯一约束冲突。

**建议**：执行阶段**重新校验唯一性约束**（与 INSERT 在同一事务内），而不只依赖预校验结果。预校验的作用是"快速发现问题"，不是"执行时免检"。这在导入导出契约中应有明确说明。

---

### C-9：删除引用保护完整性

**无异议**。所有主数据实体的 DELETE 端点均有 `_IN_USE` 错误码（409）：MATERIAL_IN_USE、WAREHOUSE_IN_USE、LOCATION_IN_USE、SOURCE_IN_USE、ROLE_IN_USE、ATTACHMENT_IN_USE。附件契约的引用保护特别正确——"已关联业务禁止删除"。

**建议**：`_IN_USE` 检查在 DELETE 事务内完成（查询关联表是否存在引用行），避免检查与删除之间的时间窗。

---

### C-10：编号耗尽 (NUMBER_EXHAUSTED) 的处理

**无异议**。通用规范 2.9 定义了 `onExhaustion: THROW`（默认），seqLen=3 日上限 999——对当前 2000 单/天的规模绰绰有余。BATCH 的 seqLen=3 按物料+天重置同样充裕。TXN_GROUP 的 seqLen=9 几乎不可能耗尽。

---

### C-11：查询平台 filter DSL 防注入

**无异议**。通用规范 2.10 明确"全部参数化（防注入）+ 字段白名单 + 操作符白名单"。EF Core 的 LINQ 表达式树 + `Expression.Call` 动态构建即可天然参数化，不需要手动拼接 SQL。

**建议**：QueryParser 的实现按两层设计——`FilterParser.Parse(json) → FilterNode` 树，然后 `FilterNode.ToExpression<T>(ParameterExpression)` → `Expression<Func<T, bool>>`。字段名到 PropertyExpression 的映射用反射+缓存，不在表达式树中做字符串拼接。

---

## D. 结论

### 汇总统计

| 分类 | 冲突 | 缺口 | 建议 | 无异议 |
|---|---|---|---|---|
| A. 技术选型 | 0 | 2 | 2 | 1 |
| B. 数据模型/契约 | 0 | 3 | 2 | 6 |
| C. 并发一致性/边界 | 0 | 2 | 5 | 7 |
| **合计** | **0** | **7** | **9** | **14** |

### 技术结论

**整体评价：可以开工，无阻塞性冲突。** 契约批产出物（15 份契约 + 5 份 ADR + 枚举 + 数据模型 + 概念设计 + 标签规范）之间一致性良好，核心设计——统一入库单表 + 类型路由、编号服务原子自增、物理库存乐观锁、复式记账流水——概念清晰、落地路径明确。

**开工前建议解决的 3 个高优先级缺口**：

1. **Batch 状态枚举补充**（B-6）：缺一个枚举定义，工作量极小但遗漏会造成实现时猜测。
2. **Receipt 状态流转文档化**（B-7）：收货单 RECEIVING→CHECKING→PUTAWAY→DONE 的推进条件目前只能从行状态推断，缺少显式状态机定义。
3. **Idempotency-Key 存储机制**（C-4）：通用规范定义了语义但未定义实现方案，应补入实现约定（表结构 + TTL + 竞态处理）。

**建议随开工同步解决的 3 个实现细节**：

1. 附件存储路径分桶策略（A-2）——避免单目录性能问题。
2. 导入执行阶段重校验唯一性（C-8）——补防预检-执行间竞态。
3. TxnGroup.type 枚举补充（C-2）——流水分类依赖此字段。

其余缺口和建议均可在实现过程中按需确认，不阻塞开工。
