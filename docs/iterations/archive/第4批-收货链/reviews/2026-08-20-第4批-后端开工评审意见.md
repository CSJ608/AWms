## 二、总体判断

第 4 批的产品流程、界面规格、主状态机和核心事务方向已经成形：收货入待检、质检待检转可用、上架暂存转目标库位均要求库存和流水同事务，PO 严格、PR/OT 宽松、REJECT 保持待检并禁止上架等关键裁决清楚。

但后端若按当前草案直接实现，仍会在以下位置被迫自行猜规则：

1. 有预建单收货时，PDA 扫入的来源批号、生产日期、效期等批次属性没有请求字段承载。
2. 唯一码标签支持 `qtyPerCode`，但 `UniqueCode` 数据模型没有数量字段，收货请求也没有定义 `quantity` 与 `uniqueCodes` 数量之和的校验规则。
3. 单据二维码解析未明确返回 `inboundOrderId` 和行列表 DTO，PDA 扫码后无法稳定进入 `POST /api/receipts` 所需上下文。
4. 打印契约提供 `PrintJob` 和 `GET /api/print/jobs/{id}/file`，但数据模型只有 `PrintLog`，缺少打印作业、文件和打印项的持久化关系。
5. 质检、上架、唯一码勾销等“一行只能处理一次”的数据库唯一约束和并发保护未在数据模型中列明。

现有 `backend/` 基线没有第 4 批实体或端点；已具备认证权限、主数据、批次查询、编号服务、查询 DSL、幂等过滤器、PostgreSQL Testcontainers 集成测试等基础能力。后端实现不需要推翻基线，但幂等过滤器当前在业务动作外预留/完成记录，第 4 批写侧若要求“业务与幂等同事务”，需要在实现中调整为服务层事务内闭合，不能直接照搬全局过滤器作为库存入账的唯一幂等保障。

## 三、阻塞问题

### P0-1 有预建单收货缺少批次属性承载

`docs/api/收货.md` 中 `POST /api/receipts` 的有预建单请求只包含：

```json
{ "warehouseId": "...", "stagingLocationId": "...", "inboundOrderId": "...",
  "lines": [{ "orderLineId": "...", "materialId": "...", "quantity": "...", "uniqueCodes": [] }],
  "photos": [] }
```

但工作流和标签规范要求供应商/生产外标签的 `rb/pd/ex/rt/rc` 扫入留档，用于生成或复用批次属性。当前只有无预建单请求定义了 `batchProps`。这会导致 PO 场景中扫到供应商批次、生产日期、效期后，后端没有契约字段可接收，只能丢弃或自造字段。

建议：有预建单收货行同样允许 `batchId?` / `batchProps?`，并明确 `t=S`、`t=B`、无码手选三种来源下批次生成/复用优先级。

### P0-2 唯一码数量模型不足，库存守恒不可验证

`docs/api/打印.md` 允许 `POST /api/print/unique-labels` 传 `qtyPerCode`，标签内容含 `q`；但 `docs/api/数据模型-草案.md` 的 `UniqueCode` 只有 `orderLineId、code、status、receivedAt`，没有 `qtyPerCode` 或数量字段。`docs/api/收货.md` 又同时接收行 `quantity` 与 `uniqueCodes?`，未定义二者关系。

这会影响：

- 唯一码每码大于 1 件时，后端无法从登记清单计算实收数量。
- 严格 PO 无法验证 `actualQty == expectedQty` 是否由唯一码清单真实组成。
- 重复提交、重复扫码和库存流水无法证明数量守恒。

建议：`UniqueCode` 增加 `qtyPerCode`，并定义 `uniqueCodes` 场景下 `quantity` 是派生值、冗余校验值还是禁止传；若保留 `quantity`，必须要求它等于已收唯一码数量之和，不一致返回稳定错误码。

### P0-3 单据二维码解析结果不足以建立 PDA 收货上下文

`docs/api/标签解析.md` 对 `t=D` 写明按类型和单号路由到单据服务并返回 document，但 DTO 示例没有 `inboundOrderId`，也没有明确行列表结构。`POST /api/receipts` 有预建单必须传 `inboundOrderId`，行匹配也优先 `orderLineId`。如果扫码结果只返回 `docNo`，PDA 需要额外猜测通过列表搜索或详情接口补查。

建议：`ScanResult.document` 明确返回 `inboundOrderId/orderNo/type/warehouseId/status/lines[]`，其中 `lines[].id` 即 `orderLineId`，并声明已作废、已收完、跨仓等 warning 字段形态。

### P0-4 打印作业模型与文件端点不闭合

`docs/api/打印.md` 定义 `PrintJob`、`items[]`、`fileUrl=/api/print/jobs/{id}/file`，并要求 Web PDF 可下载/浏览器打印；但 `docs/api/数据模型-草案.md` 只列出 `PrintLog(bizType,bizId,templateCode,printedBy,printedAt)`，不足以回答：

- `PrintJob.id` 对应哪张表。
- PDF 文件路径、状态、生成失败原因如何保存。
- `items.content/readableText/quantity` 是否持久化，PDA 预览刷新后如何恢复。
- `PrintLog` 与 `PrintJob` 是同一实体还是审计从表。

建议：补充 `PrintJob/PrintJobItem` 或明确 `PrintLog` 承担作业实体并增加字段；同时补充 `PRINT_JOB_NOT_FOUND/PRINT_JOB_NOT_READY` 或说明统一使用 `NOT_FOUND` 的边界。

### P0-5 缺少关键唯一约束和并发防重设计

数据模型列出了部分唯一性，但对第 4 批最容易重复入账的对象没有显式唯一约束：

- `UniqueCode.code` 或 `(orderLineId, code)` 唯一。
- `QualityCheck.receiptLineId` 唯一，保证同一收货行只质检一次。
- `PutawayRecord.receiptLineId` 唯一，保证同一收货行只上架一次。
- `StockLedger(txnGroupId, seq)` 唯一，保证复式流水组内顺序可追溯。
- `InboundOrderLine(orderId, lineNo)`、`ReceiptLine(receiptId, lineNo)` 唯一。

仅靠服务层先查再写，在并发请求和幂等 key 缺失/不同 key 场景下不足以证明不重复入账。建议在数据模型和迁移要求中显式补齐唯一约束、外键索引、状态/时间索引，并要求集成测试覆盖并发双提交。

## 四、非阻塞问题与实现注意

1. 附件 `bizType` 同时有 `QUALITY_CHECK` 与 `EXCEPTION`，但质检异常照片由 `QualityCheck.photoIds` 返回。建议明确收货照片、质检 PASS 照片、异常照片分别关联到哪个 `bizType/bizId`，避免删除保护和照片查询口径不一致。
2. `POST /api/quality-checks/{checkId}/resolve` 的 PASS 会执行待检转可用库存变化，但错误码未列 `INSUFFICIENT_STOCK` 或 `VERSION_CONFLICT`。若实现选择状态条件更新即可不暴露；若依赖物理库存版本，应补错误码。
3. PDA 质检规格写“扫批次标签 t=B 直接定位行”，但批次标签只含物料+批次+数量，不含 `receiptLineId`。同仓同物料同批次存在多个待办时应定义返回多候选还是提示选择。
4. 入库单和收货单涉及 `sourceType/sourceCode`，当前契约未明确是否必须引用 `Source` 主数据，也未列 `SOURCE_NOT_FOUND`。若允许自由填写，应在契约中写明；若必须主数据存在，应补校验和错误码。
5. 现有后端基线只注册了 `action.receiving.create` 和 PDA receiving 菜单，第 4 批实现时必须按 `docs/api/认证权限.md` 一次性补齐 8 个操作权限与 PDA qc/putaway 菜单，并补集成测试。

## 六、建议门禁处理

建议本次后端开工评审结论为：**有条件通过技术可行性，不通过实现开工门禁**。

建议先由协调者汇总并裁决以下契约修订，再重新锁定：

1. 收货有预建单行补 `batchProps/batchId` 规则。
2. 唯一码补数量字段与收货数量校验规则。
3. `ScanResult.document` 补 `inboundOrderId` 与行列表 DTO。
4. 打印补 `PrintJob` 持久化模型或明确 `PrintLog` 承担作业职责。
5. 数据模型补关键唯一约束、索引、并发版本和集成测试验收清单。

上述修订完成后，后端可按“模型/迁移 -> 入库单 -> 收货入账 -> 质检 -> 上架 -> 附件/打印 -> 权限与集成测试”的顺序开工。
